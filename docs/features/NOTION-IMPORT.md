# One-way Notion API import (Markdown v2)

**English** · [简体中文](NOTION-IMPORT.zh-CN.md)

In the sidebar, **Import → Import from Notion API** imports accessible pages, databases and data sources as local copies. New imports use `GET /v1/pages/{id}/markdown?markdown_version=v2&include_transcript=true`; the API header remains `Notion-Version: 2026-03-11`. This does not use the application's Markdown/CSV export or write back to Notion.

The source code and warnings in the preview show completion results, and modifying the cache selection will invalidate the original preview.

The current automatic scope is plain text and text mark in top-level paragraphs and headings, including code, normal links, bold, etc. It is required that the complete block of text is unique in both Markdown and Block API, that codes, links and other inline formats are consistent, and that source code boundaries are precise. The position of nested content such as repeated blocks, conflicting colors, unknown syntax, paragraphs containing atomic mentions, tables and columns will not be guessed, and the original text will be retained and prompts will be given. HTML export is not connected to this process.

## Reading and recovery order

Markdown is the text base. Page/database API reads attributes, paging Block children API confirms the real subpage and database ownership.`<page>` is always Child page, Notdown `<page-link>` Always Link to page; the block type does not change for the same target. Normal Markdown links and inline mentions do not trigger unbounded page traversal.

v2 accepts both single-line and multiline bodies in `<page>`, `<folder>` and `<database>` tags, including inside columns, and displays them according to the original block type. Formatting tags in titles provide readable names; unmodified original titles, line breaks and unknown attributes remain preserved. Previously imported multiline pages that appeared unsupported are recognized when reopened in the fixed application, without reimporting or bulk body rewrites.

v2 still supports backtick inline code. Some actual API responses also return `<code>…</code>` which are not currently documented in the official syntax: **Notdown** Provides compatible reading of attributeless, single-line forms of this form, which appear as inline code, with internal labels and links remaining literal text. Existing original text and adjacent edits retain the original tags; use standard backticks to save after directly editing the code. **Notion Markdown** mode does not enable this compatibility. Unknown attributes, missing closures and other unknown syntax can still be restored and retained, and existing files will not be migrated in batches.

For `<unknown>` confirmed by syntax scanning, first verify its **source block** Notion URL/ID, and then read and verify the identity of Block API. Directly convertible chunks use real response data; the rest try to request block ID as v2 Markdown , recursively filling in missing subtrees, and reading paged children if still unavailable. Template configures local Insert blocks buttons using readable subblocks; buttons are not executed during import.

Code fences, inline code, unknown containers, label attributes, and mentions of literal labels do not authorize additional reads or replacement by global URL. Repeated reads use caching, loops and overly deep subtrees to retain placeholders and hints. `unknown_block_ids` non-empty still allows previewing; the warning does not mean that all missing content has been restored. Block preview when truncating and not restoring ID.

### Page links and targets outside the import batch

`<mention-page>`, v2, `<mention>`, Link to page and ordinary Markdown page links share the same source ID mapping: the copy of this batch is connected first; when the target is not in this batch, the only available page with the same `notionImport.pageId` in the current vault is connected. The match does not rely on titles, nor does it select descendants of deleted pages or pages in the recycle bin.

Unimported targets retain their Notion URL in the source and their source ID in preview warnings. Multiple available copies remain ambiguous. The editor shows unresolved internal mentions and object references as gray, non-clickable “Unknown page”, “Unknown user”, “Unknown database”, “Unknown data source” or “Unknown location” labels. Ordinary URL hyperlinks, including Notion URLs, retain their text and normal web navigation without checking whether the destination exists. Mentions and Link to page do not recursively import destinations or change ownership. Notion block anchors in semantic mentions without a local block mapping appear as unknown locations; their original addresses remain available in source mode.

Localization changes only new copies in the current import. When a target is imported later, the external reference library resolves existing remote references by source identity. A unique available target restores local navigation without rewriting the original note or changing its revision. Titles alone never establish a match. Trash and its descendants are excluded; multiple copies remain unavailable until a target is explicitly chosen.

### External references and users

Open **Import → External references** to search names, types and source IDs, inspect resolution status, import batches and current remote references in note bodies/properties. Pages, users, databases, data sources and block locations have separate identities keyed by `notion:<kind>:<source ID>`. `metadata.json.externalEntities` stores source information, batches and explicit local bindings. Reference locations and availability are recomputed from current Markdown, properties, page origins and contacts. Imports extend the registry; existing notes also participate without a bulk content migration.

The panel defaults to unresolved internal references (including ambiguous matches). Enable **Include resolved references** to also see linked references. Local Wiki, Markdown page and location links participate; ordinary web URLs and registry entries with no current references are omitted. **Go to reference** opens the note containing the reference and selects that occurrence in the body, or opens its properties for a property reference. Repeated occurrences have separate buttons. The action goes to the referring text, rather than the linked target. Local link status is computed from current notes without changing their content or adding identity bindings.

Complete user objects with actual names returned by the API create local contacts with `notionUserId`. ID-only partial users remain unknown; no names, emails or permissions are invented, and no user-directory request is made. Later imports with complete profiles, or a new contact carrying the same Notion user ID, can resolve existing mentions. Later imports never overwrite or restore existing contacts, including deleted contacts.

The library can bind source users to existing contacts and source pages/databases to local objects of the same kind. Select **Match source ID automatically** to clear an explicit binding. Matching names never merge objects. Later copies cannot replace an explicit binding; deleting its target makes it unavailable, while restoring the target makes it available again. Saves require the library's `baseRevision`; conflicts preserve both versions without a forced retry. Records use the existing resource sync protocol, with the same experimental foreground-sync limitations.

If an inline database has pending edits when its external target changes, its draft remains intact and its reference becomes disabled with an explanation. Finish saving the table, then reopen the note to load the current target. A new target never replaces a table with pending input.

## Content support and remaining limitations

Explicit renumbering of ordered lists is determined by the source. For example, `2、4、5` may be returned by the Notion Markdown interface as two items of `2. ...` plus `<ol start="4">`; this means that the second item starts from 4 again. Local reading, editing and reopening all retain `start` and do not automatically merge or change to continuous numbering. Lists with color, sub-content and unknown attributes still retain the full vector and attributes, and the original response can be checked in the import archive.

The code fence is only checked against the same batch of Block API when there is a non-empty label that cannot be recognized by the language registry; the language ID, display name and alias in the menu are all considered known, and empty labels and Mermaid are also directly retained. The Markdown interface has been observed returning `shell` as `shen`: only correct unknown fence language if the complete code text is uniquely matched, retain the code, unknown attributes and original archive, and archive the correction basis. The original text will be retained when there are duplicates, ambiguities or missing matches; all `shen` fences will not be treated as Shell, and existing notes will not be modified in batches. This check works for both Notdown and official Notion Markdown import dialects, without desktop caching.

Block API reads in pages and nested containers, without making separate requests for each code block, and reuses the same batch of levels, styles, and attachments to scan the read responses. Pages with only known languages ​​will not add requests for language checking; pages with unknown tags may generate additional paging or container requests. To reduce import waits, fences that are mislabeled as another known language are not proactively corrected.

Empty language tags are handled separately from empty code bodies: fences with no language specified are not checked; fences with empty text but unknown tags such as `shen` are still checked. Labels can be restored when Markdown and Block API each have one and only one empty code block on the page; when there are multiple empty blocks, missing or ambiguous, the original text is retained, without guessing in order, without merging empty lines or filling in placeholder content.

## Storage, compatibility and limitations

The body truth is `vault/pages/*.md` , page attributes and `syntax.notionVersion: "v2"` are written to `metadata.json` . Original Markdown, API JSON and unknown fields continue to be archived to `.history/imports/<batch>/`; recovery, link and attachment modifications are only applied to the new copy, leaving the original archive unchanged. Source ID, API/Markdown versions and batches are saved in `notionImport`.

Old pages without v2 tags will continue to be read according to the original syntax, and the old text will not be migrated in batches. The old Tab nesting and code fence compatibility logic continues; fenced code, actual Tab, and unknown content cannot be treated as parent-child boundaries. The identity of the page tree, body Child page and Link to page is independent and not inferred from the title or appearance.

Import inheritance `createVault.importBatch`, only creates a copy. Page ID uses standard UUID: the normal new page is UUIDv4, and the imported page is stable UUIDv5 within the batch; pages with the same name will not be overwritten. Explicit migration of old ID see[vault metadata](VAULT-METADATA.md#page-uuid-migration). The same selection, recovery data, attachments and source snapshots produce the same batch; repeated submissions do not overwrite local modifications.
