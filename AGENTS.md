# Notdown

**English** · [简体中文](AGENTS.zh-CN.md)

- Directory responsibilities and file placement are defined in `docs/architecture/REPOSITORY.md`; the documentation entry point is `docs/README.md`. Unit and service tests belong in `tests/unit/`, browser tests in `tests/e2e/`, and local execution logs in `.run/logs/`, never the repository root.

This project is independent of the upstream clones in its parent directory. SiYuan is a reference for the local kernel; AFFiNE and AppFlowy are references for block interactions. The editor uses a single ProseMirror document and a custom Markdown codec. Do not describe the implementation as a complete fork of any upstream application.

- Document bodies are authoritative in `vault/pages/*.md`, not cached block JSON. Shared page properties are stored in `vault/metadata.json`; document YAML or Pandoc title blocks override the JSON defaults. Source mode shows the complete file and does not automatically add application YAML. Preserve existing files and unknown fields.
- Write through `createVault`. Every update uses `baseRevision`; conflicts must retain two recoverable versions. Never automatically force a retry because revisions differ.
- `vault/` contains user content. Tests use temporary vaults. Only `seedNewDefaultVault` creates default demonstration content, on first startup.
- Capture pending editor input before switching views. External background refreshes must not mix an old DOM body with a new revision. Drafts from different windows must not overwrite each other.
- Markdown extension rules are in `docs/FORMAT.md`. Avoid global regex rewrites of code fences or unknown syntax. Structured edits require original-source preservation and validation at malformed boundaries.
- Notdown combines existing Markdown dialects and Notion. Custom body syntax may only fill gaps in official Enhanced Markdown for Notion blocks, existing block attributes, inline content and styles, and may only be enabled with `syntax.variant: notdown`. `notion-markdown` enables only officially documented syntax; explicit extension switches cannot cross that boundary. Reuse an existing dialect where it can express the content instead of inventing a duplicate protocol. Preserve recoverable old files and unknown fields. Do not bulk-migrate user content. See `docs/audits/CUSTOM-SYNTAX-AUDIT-2026-09-23.md`.
- The authoritative MyBase repository is `D:/Workspace/mybase`. Do not write to it or allocate its LQ/LP IDs unless the user explicitly asks. Exports follow the stable UUID identities and actual datatype rules in `src/integrations/mybase.ts`.
- Install with `npm ci`, run with `npm run dev`, and validate with `npm test` and `npm run build`. Editor interaction changes also require `npm run test:e2e`. Browser tests use an independent temporary vault and Chrome, without connecting to the user's browser.
- Local CAS and conflict branches continue to protect all writes. Cross-device sync is an experimental foreground feature requiring configured Supabase or WebDAV. Do not claim production sync or guaranteed background synchronization without real cloud and physical-device acceptance. See `docs/features/CLOUD-SYNC.md`. Update feature documentation and READMEs according to the rules below.

## README maintenance

- `README.md` (English) and `README.zh-CN.md` (Chinese) are product entry points for new users. Keep this reading order: project icon, name and one-sentence introduction → main features → quick start → file storage → current status and key limitations → documentation → development and acknowledgments. The first screen must explain what the app is, what it does and how to start.
- Keep both versions short and easy to scan, with matching structure and capability boundaries. About 100–150 lines per language is a guide; do not use oversized paragraphs, giant tables or collapsed sections to evade that limit. List only a few user benefits, each in one or two sentences. Use the existing `src/assets/notdown-icon.png`, retain language switching and working navigation, and do not invent download links, badges or screenshots.
- Do not use a README as a changelog, work log, acceptance report or implementation notebook. Do not append details of the current fix before the introduction, in a feature table, in limitations or at the end of the file. Menu inventories, interaction states, pixel or latency values, node types, serialization syntax, migration commands, APIs, test configuration and individual verification results do not belong in root READMEs.
- Update existing topics first: user instructions in `docs/features/`, architecture and development configuration in `docs/architecture/`, syntax and API references in `docs/reference/` (the body contract remains `docs/FORMAT.md`), audits in `docs/audits/`, and dated acceptance records with a defined scope in `docs/verification/`. Local logs go in `.run/logs/`. Register a genuinely necessary new topic in `docs/README.md`; do not create duplicate explanations.
- Each feature change updates its corresponding topic first. Make concise, matching README changes only when user value, first-use steps or a key capability boundary changes. Ordinary fixes do not need homepage edits. Do not accumulate historical fixes as feature descriptions or present planned, partial or unverified capabilities as complete.
- Move useful instructions removed from a README into the appropriate topic, removing duplication and obsolete material. Repair internal links and heading anchors. Before submitting, read both READMEs and check the icon, relative links, startup commands and language consistency. Preview layout changes to ensure the homepage remains a readable product entry point.

## Documentation languages

- English is the canonical documentation language. Default `.md` files, including `docs/README.md`, contain English. Chinese translations use the same basename with `.zh-CN.md`; `docs/README.zh-CN.md` is the Chinese index.
- Update the English source and Chinese counterpart together. Each document provides a language switch. English README and document links stay in English; Chinese links stay in Chinese, except explicit language switches and links to source code or test data.
- Preserve code fences, inline code, commands, identifiers, paths, numeric results and historical scope while translating. Markdown fixtures are test inputs: do not translate or rename them. Their explanatory READMEs have bilingual versions.
- Validate documentation pairs, local links, heading anchors and language routing with `npm run docs:check`. Documentation-only changes do not require rerunning application interaction tests.
